01 · System

End-to-end flow

A customer folder is ingested into one Dossier. The engine retrieves memory, runs 3 parallel specialists, hands their opinions + the docs + tools to an agentic orchestrator, gates on confidence, then writes the decision back to memory — always evicting the working scratchpad on the way out.

03 · Topology

Parallel specialists → one agentic orchestrator

The hybrid design: three memory-fed specialists run in parallel (fast, focused — one call each), then a single agentic orchestrator holds their opinions + the original documents + tools and does the deep, adaptive investigation. Parallel speed for the gather; agentic depth for the decision.

04 · Orchestration

The agentic orchestrator — a serial tool-calling loop

Not one prompt — a ReAct loop. One tool call per turn (parallel_tool_calls=False), bounded by agent_max_steps. The agent reads facts, inspects transactions, runs an advisory pattern scan, reads documents, notes to working memory, and finally calls finalize. The ordered trace is the audit.

flowchart LR
  A["build_tools(dossier)
bind_tools · serial"]:::llm --> L{{"loop ≤ max_steps"}}:::store
  L --> T["model picks ONE tool"]:::llm
  T --> EX["execute + note to scratchpad
append result to context"]:::mem
  EX --> C{"near step
budget?"}:::store
  C -->|"no"| L
  C -->|"last 2 turns"| FO["offer ONLY finalize"]:::llm
  FO --> F["finalize(score, confidence,
rationale, key_signals, evidence_refs)"]:::llm
  T -->|"finalize"| F
  F --> CHK{"evidence_refs
cited by a tool?"}:::store
  CHK -->|"no · once"| L
  CHK -->|"yes"| OUT["RiskFinding + trace"]:::store
  L -.->|"exhausted"| HUM["route to human
(specialists' score, conf 0)"]:::human

🔎 Investigation tools (facts only)

read_kyc · list_documents · read_document · query_transactions (whitelisted) · aggregate_transactions · find_txn_patterns (advisory candidates + strength).

🧠 Memory + terminal tools

note / read_notes (Redis scratchpad) · finalize — the only decision-emitting tool; band is re-derived from the score server-side so it can't contradict.

Guards are loop hygiene, not scoring rules: citation check on evidence, finalize-only in the final turns, bounded loop / exception → human at confidence 0 (never blank). temperature=0. Code: ai/agent.py, ai/tools.py.

05 · The star · Memory

Layered memory — 5 tiers across 3 stores

For a single LLM call, "memory" = what you retrieve and inject into the prompt. Each tier has a different access pattern, so each lives where it fits. Working memory is the agent's scratch paper; the durable record and the learned knowledge live elsewhere.

TierWhatStoreHow it's used
Workingthe agent's evolving run notes Redis scratchpadwrite/read during the loop; evicted on every exit (complete / handoff / exception)
Per-customerthis customer's assessment history relational (SQLite→PG)history(cid) — detect change ("last quarter LOW, now £40k cash")
Episodicsimilar past cases + corrections case-bank (feature-match)top-k similar as few-shot; drawn from human-verified cases (anti echo-chamber)
Semantictypology defs, higher-risk lists reference filesstatic cheat-sheets injected into specialist prompts
Procedural"lessons learned" lessons tabledistilled from corrections by frisk reflect; injected into the orchestrator

06 · Human-in-the-loop

Confidence gate & the teach-the-model loop

Confidence decides the exit. Confident cases auto-dispose by band; unsure ones become a real message on a Redis queue. The reviewer's correct score is stored as a human-verified episode and distilled into lessons — so the human improves exactly the cases the model was least sure about.

flowchart LR
  IN["finalized score
+ confidence"]:::llm --> GATE{"confidence ≥ 0.60?"}:::store
  GATE -->|"yes"| BAND["auto-dispose by band
<15 clear · <40 jr review · <70 sr review · ≥70 escalate"]:::store
  BAND --> ESC["🚨 ESCALATE"]:::danger
  GATE -->|"no"| PR["PENDING_REVIEW"]:::human
  PR --> RQ[["Redis review queue"]]:::human
  RQ --> HU(("👤 reviewer
sets correct score")):::human
  HU --> FB["feedback.jsonl + human-verified episode"]:::mem
  FB -. "frisk reflect" .-> LES["lessons"]:::mem
  LES -. "injected next run" .-> AG["orchestrator prompt"]:::llm

07 · Reflection

What changed from the earlier design

The previous build used a deterministic rules engine as the source of truth with the LLM as an advisory cross-check. This rebuild goes fully LLM + agentic and adds a memory system.

DimensionBefore (rules + advisory LLM)Now (fully-LLM agentic)
Who scoresdeterministic score_customer()the LLM agent (tools + full context)
Typologiesrules that fire and add pointsadvisory candidates the LLM judges
Sanctionshard kill-switch railremoved (scoped out of the brief); PEP kept
Explainabilitydriver contributions summing to the scorethe tool-call trace + cited evidence
Reliabilityrules-only fallbackbounded loop → human (API assumed reliable)
Learningfew-shot from corrections5-tier memory + reflection lessons
