0 · How to make it all happen

# install the package (editable) + optional extras
pip install -e ".[llm,ui,observability,dev]"

# regenerate the deterministic dataset, run tests, launch the UI
frisk generate                       # -> data/dossiers.json (+ self-check)
pytest                               # 16 tests
streamlit run src/frisk/ui/Home.py   # Queue -> Case -> Audit

# handy CLI
frisk score --offline                # rules-only ranked queue, no LLM
frisk warm                           # populate the LLM cache for an instant UI

Everything is driven by env / .env (prefix FRISK_); keys like NVIDIA_API_KEY are read without the prefix and never committed. With no keys the engine still runs (mock / rules-only) — it never hard-fails.

1 · How the codebase is structured

An installable src-layout package (src/frisk/), one folder per concern, every stage speaking a single typed contract (core/models.py). This mirrors the production projects it was modelled on (DocGuard/EagleAI/QDMS): deterministic core = source of truth, LLM behind a provider boundary, thin UI over engine output.

2 · How it's wired (config, paths, providers)

Config = one place, env-bound, safe defaults

config/constants.py holds the domain knob (weights/floors/bands/routing — what a compliance team recalibrates). config/settings.py is a pydantic-settings Settings for everything environmental (provider, model, scale, keys). config/__init__.py assembles them into one CONFIG so call sites just do from frisk.config import CONFIG.

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_prefix="FRISK_", env_file=".env")
    provider: str = "nvidia"        # FRISK_PROVIDER
    crosscheck_policy: str = "all"  # all | gated  (the scale lever)
    workers: int = 16
    nvidia_api_key: str | None = Field(default=None, validation_alias="NVIDIA_API_KEY")  # no prefix; out of git

Provider boundary — the only LLM abstraction

Nothing outside ai/providers knows which model answered. A one-line config change swaps NVIDIA ↔ Gemini ↔ Claude ↔ a deterministic mock.

class Provider(ABC):
    def available(self) -> bool: ...           # key present?
    def complete(self, prompt, schema): ...      # structured single call (pydantic)
    def chat_model(self): ...                    # a LangChain model for the graph (or None)

get_provider("nvidia")  # factory picks by settings.provider; caches the singleton

3 · The data-ingestion pipeline — configurable for scale

Ingestion is a funnel: raw inputs become validated Dossier objects, scored, and written to a read store the UI queries. The same code path scales from 20 to 10k+/day by turning config knobs — no rewrite.

The three scale knobs (all in config)

KnobEffect
crosscheck_policy = gatedLLM only on the ~10–20% MED band; LOW auto-clears & HIGH escalates on rules alone. The LLM is the only expensive part — this is the cost lever.
workers = NThreadPool size for the I/O-bound LLM calls (overlap them; cap for rate limits).
disk/Redis cache (prompt-hash keyed)Never re-score an unchanged customer; auto-invalidates when the data (hence the hash) changes.
Why this scales: the deterministic rules score everyone at ~1,700/sec (~147M/day/core) — effectively free. Only the gated slice hits the LLM, in parallel, cached. To go from 10k→1M/day you change infra behind stable interfaces: SQLite→Postgres (store.py), ThreadPool→Celery/Kafka consumers (pipeline/batch.py), JSON cache→Redis. See docs/SCALING.md.
def assess_all_scaled(dossiers, workers=None, policy=None, persist_db=True):
    def one(d):
        rr = score_customer(d)                          # cheap, deterministic — runs on everyone
        return engine.assess(d, use_llm=should_crosscheck(rr, policy))
    with ThreadPoolExecutor(max_workers=workers) as ex:
        decisions = list(ex.map(one, dossiers))
    if persist_db: store.upsert_many(decisions)          # the scalable read path
    return decisions

4 · How data gets read & translated

Read: Decimal-safe loading into the typed contract

A dossier is 5 data families joined per customer. On disk amounts are strings; load_dossiers reparses them to Decimal so no float ever touches the money math. Every record becomes a typed Dossier — nothing crosses a module boundary that isn't one of the models.py types.

def load_dossiers(path=None) -> list[Dossier]:
    raw = json.loads(Path(path or DOSSIERS).read_text())
    return [dossier_from_dict(d) for d in raw]   # Txn.amount = Decimal(str(...))

Translate: two different "views" of the same dossier

ConsumerTranslation
Rules enginereads the Dossier fields directly — exact values, Decimal money, transaction time-series.
LLMcrosscheck._features(d) flattens the dossier into a compact text summary (counts, sums, countries, sanctions/adverse headlines). Crucially it omits the rules score so the model's opinion stays independent — that independence is what makes the confidence signal meaningful.
# _features(d) — what the model sees (rules score deliberately withheld)
nationality/country: IR/IR   occupation: arms dealer   PEP: True
sanctions_hits: ['...']      adverse_media: ['...']
transactions: 31  credits: 62174  debits: 6001  cash_in: 37476
MISSING DATA: [...] (assess with reduced confidence)

5 · How we infer from it

Two independent assessments, then reconcile. The rules score is the auditable number; the LLM is an advisory, confidence-gated second opinion that never writes the arithmetic.

5a · Deterministic rules (source of truth)

Each factor/typology is a pure function Dossier → Finding | None. Order is non-negotiable: overrides first (sanctions / PEP-in-high-risk-geo force HIGH), then a weighted sum → 0–100, then bands. Typology detectors are temporal (structuring, layering, round-trip, dormant-spike). A throwing rule degrades to a recorded finding — the engine never crashes.

5b · Multi-step LLM (the graph)

Instead of one fragile call, orchestrator.py runs a LangGraph StateGraph: 3 domain analysts in parallel (KYC / transactions / screening) → synthesize (correlate) → verify (adversarial chain-of-verification) → finalize (deterministic packaging). Each node degrades independently; a dead graph cascades to the single call, then rules-only.

5c · Reconcile + route (HITL)

def route(score, flags, degraded, confidence):
    if flags & HARD_ESCALATE: return ESCALATE  # kill-switch FIRST
    disp = AUTO_CLEAR if score<15 else REVIEW/junior if score<40 else REVIEW/senior if score<70 else ESCALATE
    if disp==AUTO_CLEAR and (degraded or confidence<0.6): disp = REVIEW  # never silently auto-clear
    return disp

AUTO_CLEAR low+confident · REVIEW uncertain · ESCALATE high / kill-switch / low-confidence. Every decision — clears and escalates alike — writes an append-only AuditRecord with a sha256 input fingerprint.

5b · LLM-only scoring & the human-in-the-loop

In the default engine_mode=llm, the LLM's score is the decision — but the system knows when it's unsure and hands those cases to a person. The one deterministic rail kept is the sanctions kill-switch.

flowchart TD
  G["5-step graph score"] --> CONF["composite confidence =
min(self-report, node-agreement, verifier)"]
  CONF --> K{"sanctions match?"}
  K -- yes --> ESC["🔴 ESCALATE (rail)"]
  K -- no --> T{"confidence ≥ threshold?"}
  T -- yes --> AUTO["auto-decide
clear / review / escalate"]
  T -- "no / LLM down" --> Q[("Redis review queue")]
  Q --> PANEL["Human Review panel"]
  PANEL --> HUMAN["reviewer sets correct
score · band · action · note"]
  HUMAN --> RES["resolve case"]
  HUMAN --> FB[("feedback store")]
  FB -. few-shot .-> G
PieceWhat it does
Composite confidencemin of the model's self-reported confidence, how much the 5 graph nodes agree, and the verifier's consistency flag. Any one being low → unsure.
Review queue (hitl/queue.py)a real Redis broker — the engine is the producer, the panel is the consumer. Falls back to in-memory if Redis is down.
Review panel (UI page)shows why the model was unsure (which analysts disagreed) + the full dossier incl. unstructured docs; the reviewer sets the correct score.
Feedback loop (hitl/feedback.py)the correction is stored and injected into future synthesis prompts as a worked example — so the model calibrates toward human judgement. This is the "get the LLM to score correctly" loop.

Offline (LLM_MODE=off) every non-sanctioned case has no real score → all route to the human queue, which is a complete demo of the panel with zero API keys.

6 · How the prompts were made production-grade

Prompts are code-owned strings (not free text scattered around), each engineered for a specific job:

PracticeWhy
Independence — the LLM is never told the rules scoreso rules↔model agreement is a real signal, not an echo. This is what makes confidence meaningful.
One narrow job per nodeeach domain analyst assesses only its family (KYC / transactions / screening); the synthesizer only correlates; the verifier only critiques. Narrow scope = fewer hallucinations.
Calibration guardrailanalyst prompts say "rate LOW when no specific red flag is present; do NOT invent risk from ordinary activity" — stops the model over-flagging benign salary-in/spend-out.
Structured output, schema-lockedevery call returns a Pydantic model (SourceFinding/RiskFinding/Verdict) via json-mode; the band is derived from the score so the model can't contradict itself (it once returned "Critical" — coerced deterministically).
Chain-of-verificationa dedicated QA node adversarially re-checks the synthesis against the evidence and can correct the score — no single generation is trusted.
Deterministic reproducibilitytemperature 0; every response cached by prompt hash. Same input → same output.
# a domain-analyst prompt (calibrated, single-domain, schema-locked)
"You are an AML {domain} analyst. Assess ONLY the {domain} risk ... respond in JSON with
 keys domain,risk_level,signals,note. Be calibrated: rate LOW when no specific red flag is
 present. A normal pattern (domestic salary-in / card-out, complete KYC, clean screening) is
 LOW — do NOT invent risk from ordinary activity."

7 · How results are shown

Note: the UI is Streamlit, not Gradio. It's deliberately a thin, read-only layer over the engine's Decision/AuditRecord objects — it contains no business logic. That means a Gradio front-end would be a drop-in alternative: point it at the same store.query() / engine.assess outputs. Swapping UI frameworks changes nothing in core/ai.

ui/Home.py = three st.navigation pages, all reading precomputed decisions:

ViewShows
Triage Queueranked st.dataframe (risk progress bars, 🟢🟡🔴 disposition), metric tiles, and a natural-language search box (nlquery → a whitelisted filter spec, never eval).
Case detailthe dossier, the driver bars that sum to the score, findings + evidence, the multi-step reasoning panel (3 domain analysts + QA verdict), and Approve / Escalate buttons (maker-checker sign-off).
Audit trailthe append-only decision log — every clear and escalate, with fingerprint + ruleset version.

Bootstrap scores once (cache-warm → instant) and writes to the SQLite store; the pages query the store, never re-score on reload. That read/compute split is exactly what lets the UI stay responsive at scale.
